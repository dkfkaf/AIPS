# A2 — 양방향 Flow 추적 설계안

상태: 사용자 승인 후 2026-11-06 구현·검증 완료. [실행 기록](../../a2-validation-2026-11-06.json)을 참고한다.

## 목적과 기존 기준

기존 A1이 만든 `ParsedPacket`을 사용해 요청과 응답을 같은 `flow_id`로 묶고, 방향별 통계와 유휴 만료·개수 제한을 제공한다. 근거는 [PROJECT_SPEC.md](../../../PROJECT_SPEC.md)의 F-02·8.1절과 [IMPLEMENTATION_PLAN.md](../../../IMPLEMENTATION_PLAN.md)의 A2다. 선행 A0·A1은 [A1 검증 기록](../../a1-validation-2026-11-05-linux.json)에서 완료를 확인했다.

C++20, 단일 처리 스레드, 기존 시스템 의존성을 유지한다. A3 TCP 재조립, 룰, JSONL 이벤트, live/Inline, Python·AI·IPC는 범위 밖이다. 현재 AIPS 폴더의 미커밋 A0·A1 변경을 보존하고 이 기준선에 이어서 작업하는 방식을 제안한다. 자동 커밋·push는 하지 않는다.

## 접근 방법

1. **제안: 정규화 키 + unordered_map + 만료 시 순회.** 명세의 해시 테이블 요구를 따르며 보조 인덱스 없이 상태와 메모리 상한을 검증하기 쉽다. 매 패킷의 만료 확인은 활성 Flow 수에 비례하므로 고속 처리 성능을 주장하지 않는다.
2. **대안: 동일한 해시 테이블 + 만료 순서 목록.** 만료 처리 비용을 줄일 수 있지만 두 자료구조의 원자적인 갱신·삭제와 추가 메모리 관리가 필요하다. A2의 정확성 확인 이후 성능 측정에서 필요하면 검토한다.

사용자는 첫 번째 방식의 설계와 현재 AIPS 폴더에서 직접 구현하는 진행 방식을 승인했다.

## 식별과 수명

- `FlowEndpoint`는 숫자 IPv4 주소와 포트다. 두 endpoint를 주소·포트 순으로 정렬한 `FlowKey`에 프로토콜을 포함한다. 키의 동등 비교와 해시는 모든 필드를 사용한다.
- 정렬은 식별용이다. 통계의 `fwd`는 명세대로 **처음 관측한 패킷 방향**이고 역방향이 `bwd`다. 두 endpoint가 완전히 같으면 방향을 구별할 수 없어 fwd로 집계한다.
- `flow_id`는 테이블 수명 동안 재사용하지 않는 64비트 양의 정수다. 만료된 키를 다시 관측하면 새 ID를 배정한다. 숫자 범위를 넘기거나 자원을 확보할 수 없으면 명확한 오류로 처리한다.
- 기본 최대 엔트리는 10,000개, 유휴 만료는 120초다. 둘 다 양수여야 하며 설정 구조체와 CLI 옵션으로 바꿀 수 있게 한다.
- 새 패킷을 처리하기 전에 유휴 엔트리를 제거한다. 유휴 간격이 설정값 **이상**이면 만료한다. 공간이 없으면 기존 Flow는 계속 갱신하되 새 Flow 추적은 거부한다. 활성 Flow를 임의로 축출하지 않는다.
- 만료 시계는 지금까지 관측한 캡처 시각의 최댓값으로 유지한다. 역순 시각이 와도 시계를 되돌리지 않으며 해당 관측은 현재 논리 시각의 활동으로 처리한다. Flow의 캡처 시작·마지막 시각은 실제 타임스탬프의 최솟값·최댓값을 따로 보관한다. 역순 입력의 만료는 이 정책에 따른 근사임을 문서화한다.
- A2의 Flow 수명은 유휴 만료로 구분한다. FIN/RST 상태는 기록하지만 도착 즉시 엔트리를 제거하지 않는다. 만료 전 같은 5-tuple을 다시 사용한 연결이 합쳐질 수 있다는 한계를 명시한다.

## 보관 상태와 핵심 인터페이스

`include/miniips/flow.hpp`에 endpoint·key·방향·통계·스냅샷 값을 정의하고, `flow_table.hpp`와 `src/flow_table.cpp`에 테이블의 상태 변경을 모은다.

- 방향별 패킷 수와 바이트 합계. 바이트는 Ethernet이나 payload가 아닌 **IPv4 Total Length**다.
- 캡처 시작·마지막 시각, 방향별 마지막 시각과 IAT 집계, SYN/ACK/RST/FIN/PSH 관측 카운터. 음수 시각은 거부하며 역순 IAT는 0으로 처리하고 마지막 시각을 되돌리지 않는다.
- 단순 TCP 상태: 관측, SYN 관측, 양방향 handshake 관측에 따른 연결 추정, 종료 중, 양방향 FIN 종료, RST. 시퀀스/ACK 번호를 검증하는 완전한 TCP 상태 머신은 아니다. UDP에는 TCP 상태를 부여하지 않는다.
- 패킷·payload·문자열·가변 길이 스트림 버퍼는 보관하지 않는다. Flow별 상태 크기는 고정이며 전체 엔트리 수로 메모리를 제한한다. IAT와 flag 집계는 후속 특징 추출을 위한 원시 상태이며 AI 특징 벡터나 추론 코드는 만들지 않는다.

제안 인터페이스:

```cpp
FlowKey make_flow_key(const ParsedPacket& packet);

class FlowTable {
 public:
    explicit FlowTable(FlowTableConfig config = {});
    FlowResult observe(const ParsedPacket& packet);
    std::size_t expire(std::chrono::microseconds now);
    std::optional<FlowSnapshot> find(const FlowKey& key) const;
    FlowTableStats stats() const noexcept;
    std::size_t size() const noexcept;
};
```

`FlowResult`는 추적 결과와 `CapacityExceeded` 오류를 구별하는 variant다. 추적 결과에는 값으로 복사한 `FlowSnapshot`, 방향과 신규 생성 여부를 둔다. 외부로 map 원소의 포인터·참조를 반환하지 않아 만료 후 참조 수명 문제를 피한다. 잘못된 설정·메타데이터와 숫자 범위 오류는 예외로 명확히 구별한다.

## CLI와 파일 변경 범위

- `src/cli.cpp`: 파싱 성공 패킷을 `FlowTable`에 전달하고 기존 메타데이터 뒤에 `flow_id`와 `direction`을 출력한다. PCAP 분석 종료 시 생성·활성·만료·추적 거부 건수를 추가로 출력한다.
- 선택 옵션 `--max-flows N`, `--flow-idle-timeout-seconds N`을 추가한다. 누락·중복·0·음수·숫자 범위 초과는 기존 사용법 오류 코드 2로 거부한다. 기존 `--help`, `--version`, PCAP 필수 옵션과 오류 코드 계약을 유지한다.
- 테이블 상한에 걸린 패킷도 파싱된 메타데이터는 출력하되 `flow_id=untracked`와 추적 거부 건수·오류 원인을 표시한다. 파일을 끝까지 읽었다는 종료 코드 0을 전체 Flow 추적 성공으로 표현하지 않는다.
- `CMakeLists.txt`, `tests/CMakeLists.txt`: Flow 라이브러리·테스트와 포맷 검사 대상을 연결한다.
- `tests/test_flow_table.cpp`, `tests/test_cli_flow.cpp`: 아래 검증을 추가한다. 요청·응답 PCAP은 기존 독립 fixture 도구로 테스트 중 생성하며 원본 PCAP은 커밋하지 않는다.
- README와 `docs/design-decisions.md`, `docs/known-limitations.md`, `docs/test-plan.md`: 기본값·시간/용량 정책·실제 실행 결과를 기록한다.

## 검증 계획과 완료 조건

1. 동일 방향·역방향은 같은 ID, 포트·프로토콜이 다르면 다른 ID. 최초 관측이 정렬된 키의 반대 방향인 경우도 fwd를 정확히 유지한다.
2. IP 바이트 합계, 양방향 카운터·IAT·TCP flag와 단순 연결 상태를 독립적으로 확인한다.
3. 120초 직전/정확한 경계/직후, 역순 시각, 유휴 제거와 동일 키 재등장 시 새 ID를 확인한다.
4. 최대 개수에서 기존 Flow 갱신, 새 Flow 거부, 만료 후 공간 재사용과 고정 상태 보관을 확인한다.
5. CLI의 요청·응답 PCAP에서 같은 ID와 반대 방향을 확인하고, 설정 오류·용량 거부·파싱 오류 후 지속 처리를 검증한다.
6. 새 테스트 실패를 먼저 확인한 뒤 최소 구현을 진행한다. 기존 67개 회귀 검사와 새 테스트, Debug·Release/clang-tidy·포맷·ASan/UBSan을 실제 실행한다.

요청/응답의 동일 ID와 만료 후 정리를 실제로 재현하고 위 검사 결과를 기록한 뒤에만 A2 완료로 판정한다. 다음 A3는 별도 지시 후 진행한다.
