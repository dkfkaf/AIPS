# A4 — JSON 룰 엔진 설계안

상태: 2026-11-07 승인 후 구현·인수 검증 완료. 패턴별 KMP를 사용했고 세 구성 각각184/184와 포맷 검사를 통과했다. [실행 증거](../../a4-validation-2026-11-07.json)를 참고한다. 중요 리뷰2건은 수정했고 경미3건은 기록했다. IPS 완성 후 사용자 자체 테스트를 거쳐 AI 단계로 넘어가는 진행 결정을 상위 문서에 유지한다.

## 목적과 현재 기준

오프라인 IPv4 TCP/UDP 패킷과 A3의 관측 TCP prefix에 소형 JSON 룰을 적용해 결정적인 alert/pass/drop 결과를 만든다. [PROJECT_SPEC.md](../../../PROJECT_SPEC.md) F-04와 [IMPLEMENTATION_PLAN.md](../../../IMPLEMENTATION_PLAN.md) A4가 기준이다. 선행 A0~A3는 [A3 실행 증거](../../a3-validation-2026-11-07.json)의 Debug·Release/clang-tidy·ASan/UBSan 각각 146/146로 확인했다.

기존 C++20, nlohmann/json 시스템 의존성, 단일 스레드, 현재 AIPS 폴더의 직접 구현·검증·최종 독립 리뷰 방식을 유지한다. 미커밋 기존 변경을 보존하고 자동 commit/push는 하지 않는다. A5 JSONL·일반 파이프라인 재구성, live/Inline·실제 DROP·AI는 범위 밖이다. A3의 경미 보류 2건은 이번 룰 엔진과 별개로 유지한다.

## 접근 방법

1. **제안: 정렬된 불변 룰 + 관련 스트림 구간 검색.** priority/sid 순서로 packet payload 또는 현재 관측에 관련된 first-seen prefix 구간을 검사한다. 중복 이벤트 억제와 매 패킷의 Allow/Drop 판단을 분리한다. 순서·재전송·갭 보충의 의미를 명확히 검증할 수 있다.
2. **대안: 매 패킷마다 누적 prefix 전체 검색.** 코드가 단순하지만 이미 본 패턴이 순수 ACK나 무관한 뒤 데이터에도 계속 적용될 수 있다. 이를 피하려면 별도의 흐름 전체 정책이 필요한데 현재 명세는 그런 영구 pass/drop을 요구하지 않는다.

사용자는 첫 번째 방식과 기존 KMP 설계안을 선택했다. Aho–Corasick은 다중 패턴의 합리적인 대안이지만 이번 구현에는 도입하지 않는다. 검색 비용은 룰 수에 비례하며 실측 성능을 보장하지 않는다. 정규식·OS별 정규화·멀티스레딩도 범위 밖이다.

## JSON 계약과 로딩

- 루트는 `{"rules":[...]}` 객체다. 빈 배열은 유효하다. sid/enabled/priority/action/protocol/scope/content/message는 필수이고 src_port/dst_port만 선택이다. 알 수 없는 필드, 중복 객체 키, 주석·잘린 JSON·뒤의 불필요한 토큰은 거부한다.
- sid는 양의 uint32(1~4294967295), priority는 int32(-2147483648~2147483647), enabled는 JSON boolean이다. 소수·문자열·boolean을 정수로 변환하지 않는다. sid는 비활성 룰을 포함해 중복 불가다.
- action은 alert/drop/pass, protocol은 tcp/udp/any, scope는 packet/stream의 정확한 소문자 문자열이다. 포트는 0~65535 정수이며 null·문자열·소수는 거부한다.
- stream은 protocol=tcp만 허용한다. stream+udp와 stream+any는 로딩 실패로 한다. any+packet은 TCP/UDP 모두에 적용한다.
- content는 길이 1~4096바이트의 출력 가능한 ASCII(0x20~0x7e)이며 대소문자를 구분한다. 빈 패턴·제어문자·비ASCII는 거부한다. `\u0041`처럼 JSON에서 디코딩한 결과가 출력 ASCII인 표현은 같은 바이트로 취급한다. 바이너리 패턴·Unicode 정규화는 지원하지 않는다.
- message는 필수 UTF-8 문자열, 길이 1~1024바이트다. 콘솔에는 JSON 문자열 인코딩을 적용해 줄바꿈·ESC 등을 실제 제어문자로 출력하지 않는다. 원시 payload는 출력하지 않는다.
- 파일은 최대 1 MiB, 룰은 비활성 포함 최대 1024개, JSON 중첩 깊이는 최대 8로 제한한다. 파일 크기 통계만 믿지 않고 최대+1바이트까지만 읽고 거부한다. 파서의 깊이/중복 키 검증도 전체 DOM 생성 전에 동작시켜 과도한 중첩을 방치하지 않는다.
- 전부 검증한 뒤 불변 RuleSet을 생성한다. 하나라도 잘못되면 전체 로딩 실패이며 일부 룰로 분석을 계속하지 않는다. disabled 룰도 스키마 검사를 한다. 로딩된 뒤 수정·hot reload는 지원하지 않는다. 로드 오류에는 룰 인덱스/필드를 표시하되 파일 원문을 통째로 노출하지 않는다.
- 규칙 수·문자열·파일/깊이 상한은 명세의 미정 부분에 대한 작성자 선택이다. 기본 예시 파일 `rules/example.json`은 현재 존재하지 않으므로 명세의 HELLO stream alert와 BLOCKME packet drop 두 룰을 새로 만든다.

## 헤더와 결정 정책

- 룰은 priority 오름차순, 같으면 sid 오름차순이다. JSON 배열의 입력 순서와 무관하게 같은 결과여야 한다.
- disabled 룰은 평가하지 않는다. 프로토콜·src_port·dst_port는 현재 패킷의 실제 방향에 적용하고 생략한 포트는 wildcard다. packet 룰은 L2/L3 헤더가 아닌 현재 transport payload만 검사한다.
- 일치한 alert는 RuleMatch 이벤트를 추가하고 계속 평가한다. 처음 일치한 drop은 Drop, pass는 Allow로 결정하고 아래 룰 평가를 끝낸다. 아무 terminal match가 없으면 Allow다. alert만으로 Drop하지 않는다. pass는 해당 관측의 결정이며 Flow 전체 영구 허용 캐시가 아니다.
- 룰당 한 관측에서 이벤트는 최대 1개다. 여러 위치가 일치하면 가장 큰 match end-offset을 대표로 선택한다. terminal sid는 이벤트가 중복 억제되더라도 DetectionDecision에 남긴다.
- 반복 문자가 많은 입력에서 패턴 길이만큼 검색 비용이 곱해지지 않도록 패턴별 선형 검색(KMP)을 사용한다. 실패 함수는 로딩 후 한 번 구성하고, 모든 occurrence 목록을 만들지 않고 마지막 관련 end-offset만 구한다. 전체 룰 수에 비례하는 순차 검사는 유지하며 고속 처리 성능은 주장하지 않는다.
- Flow 추적이 거부된 패킷도 packet 룰은 검사한다. stream 룰은 해당 컨텍스트가 없어 평가하지 않았음을 표시한다. parse_error 패킷은 기존처럼 건너뛰고 정상 판정으로 위장하지 않는다.

## 스트림 관련 구간과 재전송

누적 first-seen prefix 전체를 현재 패킷의 새로운 데이터로 간주하지 않는다. 검사 관련 구간은 다음 둘의 합집합이다.

1. 이번 관측에서 새로 연속이 된 `newly_contiguous`의 prefix offset 범위.
2. 이번 payload가 A3에서 허용된 위치 중 현재 연속 prefix와 겹치는 범위. 동일 재전송도 여기에 포함되며, overlap 충돌은 A3의 first-seen 바이트를 사용한다.

이 구간과 **바이트 하나 이상 겹치는 완전한 패턴**을 stream match로 인정한다. 경계의 양쪽에 최대 content_length-1만큼의 컨텍스트를 포함해 HEL/LO처럼 나뉜 패턴과 앞부분의 재전송도 검사한다. 갭을 가로질러 검색하지 않고, 아직 pending인 위치나 깊이 밖 위치를 검사했다고 보고하지 않는다. 관련 구간이 없는 순수 ACK에는 과거 stream 패턴을 다시 적용하지 않는다.

이를 위해 A3 ReassemblyUpdate에 현재 payload의 허용 prefix 범위(선택적 begin/end offset)를 추가한다. A3가 이미 아는 기준점/SEQ 검증 결과를 반환하므로 룰 엔진에 별도 시퀀스 추정기를 만들지 않는다. SYN+FIN/SYN+RST, 거부한 FIN, ambiguous sequence 등 세그먼트 전체가 거부된 경우 이 범위는 없다. 범위는 first-seen 정책상 수용한 위치를 뜻하며 충돌한 원시 새 바이트를 검사한 것으로 주장하지 않는다. disabled/reset/session_reuse 방향은 새 범위를 만들지 않는다.

새 필드는 A3의 기존 prefix·이벤트·통계 의미를 유지하며 A4에 필요한 컨텍스트만 추가한다. 직접 API에는 flow_id·방향·프로토콜 일치, 범위 정합성과 newly_contiguous가 prefix의 끝 구간이라는 검증을 둔다. 잘못된 컨텍스트는 상태 변경 전에 오류로 거부한다. 입력 span을 소유 상태로 저장하지 않는다.

## 이벤트 중복 억제와 자원

- Flow/방향/stream sid별 최고 **발행 end-offset**을 저장한다. 대표 match의 end-offset이 이전 값 이하이면 새 RuleMatch 이벤트를 억제한다. 더 앞선 과거 위치도 억제하는 보수적인 정책이며 모든 개별 occurrence의 발행 이력을 보존하지 않는다.
- 이벤트를 억제해도 terminal pass/drop 판정은 그대로 적용한다. 이미 HELLO를 탐지한 뒤 HEL 또는 LO가 재전송되면 같은 stream drop을 다시 적용할 수 있다. 반대로 payload 없는 ACK는 관련 구간이 없으므로 그 과거 match가 적용되지 않는다. packet 룰은 패킷별 평가이고 stream 중복 억제를 적용하지 않는다.
- 실제로 도달해 일치한 룰의 watermark만 갱신한다. 앞 terminal 룰 때문에 평가하지 않은 뒤 룰을 검사했다고 표시하지 않는다. 만료/EOF에 해당 Flow의 상태를 해제한다.
- 상태는 A2와 동일한 max_flows로 개수를 제한한다. 활성 stream 룰 수에 비례한 방향별 uint64 watermark 배열을 지연 할당하고, 합계 예산 기본 32 MiB를 둔다. 정확히 배열 바이트를 계상하고 map 등 고정 메타데이터는 개수 제한으로 관리한다. 전체 RSS 보장은 아니다.
- 방향 배열은 첫 stream match 이벤트를 발행하기 직전에 만든다. 미일치나 packet 룰만 사용하는 Flow에는 watermark 배열을 만들지 않는다. 룰 로딩과 검색 전처리 자료는 파일/룰/문자열 상한으로 제한하고 watermark 예산과 구별해 문서화한다.
- 예산·상태 용량을 확보할 수 없으면 명확한 detection_error로 파일 분석을 종료한다. 조용히 억제를 끄거나 정상 Allow로 바꾸지 않는다. 구성 구조체와 선택 CLI `--rule-state-bytes N`으로 양수 예산을 바꿀 수 있게 한다. 낮은 예산에서 어떤 입력까지 가능한지는 룰 수/방향 수에 따른다.
- 출력 이벤트 수는 한 관측당 활성 룰 수 이하이고 무제한 큐는 없다. 종료/예외 경로는 RAII로 정리한다. 룰 engine은 현재 FlowTable의 모든 관측/만료를 동기 순서대로 소비하는 단일 스레드 객체다.

## 모듈과 CLI 범위

- `rule.hpp`: RuleAction/RuleScope/RuleProtocol과 검증된 룰 값.
- `rule_loader.hpp`, `src/rule_loader.cpp`: bounded JSON 입력과 불변 RuleSet 생성. 외부의 임의 Rule 벡터로 검증을 우회하지 못하게 한다.
- `detection_decision.hpp`: Allow/Drop·terminal sid·이번에 발행할 RuleMatch·중복 억제 수·관측 검사 범위 정보.
- `rule_engine.hpp`, `src/rule_engine.cpp`: evaluate(현재 ParsedPacket, 선택 FlowObservation/ReassemblyUpdate)와 forget_flow/clear. 정확한 C++ 타입/컨테이너 배치는 실행 계획에서 정한다.
- CMake에 miniips_rules 라이브러리와 단위/통합/포맷 검사를 추가한다. 기존 nlohmann_json 타깃만 사용하고 새 패키지를 설치하지 않는다.
- PCAP CLI의 선택 `--rules PATH`를 추가한다. 옵션이 없으면 기존 A3 출력/분석을 유지한다. 룰 파일은 PCAP을 분석하기 전에 전체 검증한다. 사용법 오류는 2, 파일/JSON/리소스/출력 오류는 1로 구별한다.
- 룰 사용 시 bounded 콘솔 rule_match/decision 요약을 추가한다. pass/alert/drop과 terminal sid, 억제 여부를 구별하고 모든 판정에 `mode=pcap enforced=false`를 표시한다. 이것은 실제 네트워크 차단이 아니며 A5 JSONL 출력도 아니다.
- A3가 midstream/gap/limit 등의 불완전 이력을 가진 경우 그 사실을 기존 reassembly 메타데이터와 판정의 검사 범위 정보로 유지한다. no-match Allow가 전체 스트림 보안 검사를 마쳤다는 뜻은 아니다. 탐지 시점의 현재 패킷에만 결정이 귀속되고 이미 지나간 세그먼트를 소급 Drop했다고 보고하지 않는다.
- README, 설계 결정/알려진 한계/테스트 계획, 예시 룰, A4 실행 증거를 갱신한다. A5는 별도 요청 전 시작하지 않는다.

## 검증 계획과 완료 조건

1. JSON 문법·타입·필수/알 수 없는 필드·중복 키/SID·정수 경계·포트·enum·ASCII·빈 문자열·UTF-8·disabled·파일/룰 수/문자열/깊이 상한과 전체 로딩 원자성을 확인한다.
2. protocol/양방향 src/dst port·wildcard·packet payload 범위·대소문자·미일치/alert/drop/pass·priority/SID tie와 입력 배열 순서 불변성을 확인한다.
3. HEL+LO는 stream에서만 탐지하고 packet 룰은 놓치는 차이를 확인한다. 역순 갭 보충, 여러 match의 대표 end, overlap first-seen·wrap·검사 깊이·midstream 상태를 함께 검사한다.
4. 동일 재전송은 이벤트를 억제해도 drop/pass가 Allow로 뒤집히지 않아야 한다. 앞/뒤 일부 재전송도 판정하고, 순수 ACK와 무관한 뒤 데이터는 과거 패턴을 다시 적용하지 않아야 한다.
5. 방향/Flow/SID별 억제 독립성, 낮은 priority의 terminal로 건너뛴 룰의 상태, 만료 뒤 새 ID, EOF 해제, 상태 예산 경계/초과와 오류 경로를 검증한다.
6. 실제 합성 PCAP CLI와 예시 JSON으로 정상/경고/명시적 허용/시뮬레이션 Drop을 확인한다. 잘못된 룰은 분석 시작 전에 종료하며 메시지 제어문자·출력 오류도 검사한다.
7. 새 테스트 RED→GREEN 후 기존 146개를 보존해 Debug·Release/clang-tidy·ASan/UBSan 전체 검사와 포맷을 실제 실행한다. 실제 실행 파일과 비특권 계정도 확인하고, 소스/로그 해시·명령·JUnit·최종 독립 리뷰·수정 결과를 기록한다.

정상/악성 예시의 결정적 alert/pass/drop과 위 룰 테스트를 실제 검증한 뒤에만 A4 완료로 판정한다.

## 설계 검토 기록

2026-11-07 독립적인 구현 관점 검토에서 중요한 미정 계약이 없다는 결과(`nothing important left`)를 받았다. 패턴별 KMP 검색과 첫 stream 이벤트 직전의 상태 배열 할당은 작성자가 정한 세부 선택이다. 설계 승인이나 제품 구현·테스트 통과를 의미하지 않는다. 현재 변경은 이 설계 문서뿐이며 A3 검증 소스는 유지한다.
