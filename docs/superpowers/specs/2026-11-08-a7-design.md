# A7 — 격리 NFQUEUE Inline IPS 설계

상태: A7 구현·격리 검증 완료(2026-11-08). [실행 증거](../../a7-validation-2026-11-08.json)에 세 구성257/257·실제 NFQUEUE14/live11시나리오와 실제3허용/1차단을 기록한다. 세부 기본값은 작성자 선택이며 아래와 같이 명시한다. 실제 허용/차단 완료는 격리 시험 증거로만 판정한다.

## 목적과 선행 상태

NFQUEUE의 L3 IPv4 패킷을 기존 Engine에 전달하고 룰 Drop은 NF_DROP, 정상 Allow는 NF_ACCEPT로 적용한다. PacketParser/Flow/TCP/RuleEngine은 재사용한다. 판정 전달을 로그보다 먼저 수행하고, 처리/로그/종료 오류에도 유효한 queue packet ID마다 verdict를 한 번만 시도한다.

기준은 PROJECT_SPEC F-05/F-06, IMPLEMENTATION_PLAN A7, AGENTS의 격리·정확히 한 번 원칙이다. HEAD `2bc66a06acd05b0236a24b17f37818e45a4fab2b`의 A6는 세 구성238/238과 실제 live11시나리오를 검증했다. 시작 작업 트리는 깨끗했다. A7만 수행하며 A8/AI·패킷 변조·재주입·성능 최적화·전체 프로토콜 지원은 추가하지 않는다.

초기 환경 확인에서 libnetfilter_queue1.0.5와 커널 NFQUEUE/nft_queue 모듈 파일을 확인했다. nftables는 설치하지 않고 apt download/dpkg-deb extract로 ignored build-a7-work/tools 안에 실행 파일·라이브러리만 풀었다. 서비스/전역 설치/호스트 방화벽 변경 없이 임시 익명 netns에서만 table/queue rule 생성과 nfq_create_queue 바인딩을 먼저 확인한 뒤 최종 실제 패킷 시험을 수행했다.

## 접근 방식과 범위

제안은 **동기 NFQUEUE adapter → Engine → verdict adapter → 기존 발행기**다. 단일 스레드, 커널 큐1024, 고정 크기 netlink 수신 버퍼와 bounded Engine을 유지한다. 별도 worker/로그 큐는 수명·포화·종료 정책을 늘리므로 이번에 도입하지 않는다. 기존 설치·링크된 libnetfilter_queue handle API를 RAII로 감싼다. upstream이 legacy API를 deprecated로 문서화한 점은 기록하며 새 libmnl 개발 의존성/직접 netlink 프로토콜 구현은 추가하지 않는다.

현재 폴더에서 작업하고 자동 commit/push를 하지 않는다. 기존 PCAP/live 계약과238개 회귀를 유지한다. **IPS A0~A8 → 사용자 자체 테스트 → 결과 확인·AI 착수 지시 → B0** 순서를 유지한다.

## CLI와 권한

```bash
sudo ./build/miniips --mode inline --queue-num 0 --enable-inline --rules rules/a7-demo.json --log inline-events.jsonl
```

- --mode inline에는 queue-num0~65535와 값 없는 --enable-inline이 모두 필요하다. 누락·중복·범위 오류는2이며 NFQUEUE를 열지 않는다. 기존 PCAP/live에서는 두 옵션을 거부한다. --input/--interface는 inline에서 금지한다.
- --packet-count는 inline에서도 선택적으로 허용한다. 유효 ID callback 수에 도달하면 이미 수신한 netlink datagram의 나머지 callbacks까지 판정한 뒤 중지할 수 있다. 따라서 batch 경계로 제한을 약간 넘을 수 있고 미수신 커널 큐를 완전히 drain한다고 주장하지 않는다.
- 룰/Engine 설정 → 새 파일 logger → queue 활성화 순서다. root/CAP_NET_ADMIN 부족, 중복 큐 바인딩, 구성 실패는1이다. 프로그램은 nftables 규칙을 추가·삭제하지 않는다. 준비 성공 시 inline_ready를 stderr에 알린다.
- 정상 SIGINT/SIGTERM/packet-count는 Stopped, EOF 아님. main의 기존 RAII 신호 정책을 inline에도 적용한다. 라이브러리는 전역 신호 정책을 바꾸지 않는다. 실제 오류/최종 출력 실패는1이다.

## L3와 시각

PacketLayer에 Ipv4를 추가해 Ethernet 헤더 없이 같은 IPv4/TCP/UDP 길이·fragment·프로토콜 검사를 사용한다. 기존 Ethernet 경로와 오류 이름은 유지한다. NFQUEUE copy 범위는65535이며 실제 payload span보다 IP total length가 크면 불완전/파싱 오류다. payload를 변조하거나 checksum을 다시 쓰지 않는다.

inline의 관측 시각은 callback이 패킷을 받은 system_clock 마이크로초다. NFQUEUE에서 언제나 제공되지 않는 capture timestamp를 가짜로 만들지 않고 `timestamp_status=receive`로 명시한다. 기존 내부 captured_at 이름과 Engine watermark는 재사용하되 PCAP/live의 capture 시각 의미는 바꾸지 않는다. 빈/첫 패킷 전 실패는 계속 null이다. 이 시각은 커널 최초 도착 시각과 다를 수 있다.

## verdict·오류 정책

아래는 A7 작성자 정책이며 코딩 스타일만으로 암묵 선택하지 않는다.

| 상황 | 적용 | 보고 |
|---|---|---|
| 룰 Drop | NF_DROP | 성공 제출 시 실제 Drop 카운터 |
| 룰 Pass/Alert-only/no-match/룰 없음 | NF_ACCEPT | 룰 판단과 실제 verdict 구별 |
| 미지원/파싱 실패 | NF_ACCEPT | parse_error와 inspected=false/parse_error_accept verdict; 검사를 성공했다고 하지 않음 |
| Engine 예산·예외/필수 payload 없음 | fallback NF_DROP 후 중단 | 처리 오류와 fallback 카운터; 정상 Allow로 만들지 않음 |
| 로그 장애 | 이미 계산한 verdict 유지 | 한 번 진단·미기록 집계, 신호/limit까지 계속 |
| verdict 전송 실패 | 재시도하지 않고 중단 | attempted1/sentfalse, enforcedfalse/코드1 |

독립 설계 검토가 지적한 예산 구분: fatal은 기존 Engine의 `processing_error`(룰 watermark 예산 등)와 실제 예외다. Flow 용량 거부와 TCP DepthLimit/MemoryLimit/CapacityLimit 등 A3/A4의 제한 이력은 fatal로 바꾸지 않는다. 기존 packet fallback/제한 prefix 판정을 계속하며 inspection_status=limited와 경고/stream scope를 남긴다. 깊이 도달만으로 프로세스를 중단하지 않으며 이를 완전한 검사로 주장하지 않는다. 이 선택은 기존 룰 의미를 보존하는 작성자 결정이다.

VerdictGuard는 유효 ID·nothrow sender 함수 포인터/문맥·카운터를 참조하는 무할당 RAII 값이다. submit 호출 전에 attempted를 고정하고 정상/예외/반복 호출에도 sender를 한 번만 호출한다. 미제출 상태로 범위를 벗어나면 fallback Drop을 한 번 시도한다. 전송 실패 후 재시도하면 중복 적용 여부를 알 수 없으므로 하지 않는다. 단위 테스트는 성공/실패/예외/재호출을 검증하며 실제 NFQUEUE 전달은 별도로 검증한다.

NFQUEUE callback은 C 경계로 예외를 내보내지 않는다. 유효 ID를 읽자마자 guard를 만들고 inspect를 호출한다. verdict가 끝난 뒤 owned 결과/receipt를 CLI의 publication callback에 전달한다. 최초 치명적 오류 뒤 같은 수신 datagram의 나머지 유효 ID는 fallback Drop으로 처리하며 Engine을 다시 호출하지 않는다. ID가 없는 메시지는 판정을 주소 지정할 수 없으므로 missing_id로 세고 오류 종료한다. 이 경우 정확히 한 번의 성공을 주장하지 않는다.

guard의 sent는 nfq_set_verdict가 성공을 반환했다는 뜻이다. Netlink 제출 성공을 모든 후속 네트워크 전달의 보증으로 보지 않는다. 실제 Allow/Drop 성공 주장은 이번 격리 수신기 관측으로 확인한 트래픽에 한정한다. 처리 오류·전송 실패·커널/프로세스 종료의 전역 exactly-once 보장은 주장하지 않는다.

## NFQUEUE 소스와 종료

- handle/queue를 RAII 소유한다. AF_INET bind, 명시 queue bind, COPY_PACKET65535, maxlen1024, fail-open flag off를 확인한다. 다른 listener를 해제하는 nfq_unbind_pf는 호출하지 않는다. GSO flag는 켜지 않으며 대형/분할/미지원 패킷의 한계를 기록한다.
- socket은 nonblocking, 최대100ms ppoll로 정지 요청을 확인한다. netlink sender가 kernel인지 확인하고 메시지 경계/길이를 검증한다. 큰 datagram은 길이를 peek해 고정 상한을 넘으면 소비하지 않고 오류 종료한다. recv truncation/ENOBUFS/실패는 오류로 세고 전체를 성공으로 숨기지 않는다.
- per-packet span은 callback 안에서만 유효하다. 결과/receipt는 원본 payload span을 보관하지 않는다. 프로그램 전체 패킷/ID 목록이나 비동기 무제한 큐를 만들지 않는다.
- 정상/오류 종료에서 queue/handle을 한 번 닫고 close 결과를 최종 상태에 반영한다. 종료 중 주소 지정 가능한 callback이 발생하면 guard의 fallback 정책을 적용한다. source가 닫히기 전/종료 과정의 내부 소유 상태를 정리한 뒤 최종 통계를 복사한다.
- close는 run 이후 사용자 callback의 수명이 끝날 수 있어 After/Inspector를 해제한다. close 중 callback으로 받은 패킷의 fallback Drop은 최종 카운터에 포함하지만 개별 receipt 이벤트가 없을 수 있다. 따라서 오류 종료 시 actual_drop 카운터가 개별 Drop 로그 수보다 클 수 있다. 이는 시뮬레이션/성공 검사를 주장하는 것이 아니라 종료 정책의 별도 효과다.
- 통계는 callbacks/valid IDs/verdict attempts/accepted/dropped/failed/fallback/missing_id/processing/recv errors를 구분한다. 성공 시험에서는 valid IDs=attempts=accepted+dropped, failed0을 확인한다. 커널에 남은 미전달/유실 패킷을 이 등식에 넣지 않는다.

## 로그·출력

CaptureMode Inline을 추가한다. 기존 PCAP/live 출력은 유지한다. inline은 일반 publish_packet에서 시뮬레이션 verdict를 만들지 않고 OS receipt를 받은 별도 inline verdict 이벤트를 기록한다. 파싱 실패에도 실제 ACCEPT/inspectedfalse를 기록한다. 예외로 결과를 만들지 못한 receipt는 endpoint/Flow/packet_number를 추측하지 않고 null로 둔다. queue-num/queue packet ID/수신 순번·처리 상태를 별도 필드로 남긴다.

`enforced=true`는 inline의 성공 제출 verdict 레코드에만 사용한다. alert/flow/stats 자체는 OS 적용 행위가 아니므로 false다. 전송 실패 verdict는false이며 성공 카운터에 넣지 않는다. reserved enforced 키는 발행기가 우회 override하지 못하고 EventContext의 검증된 값으로 직렬화한다.

inline stats의 actual_drop_packets/actual_accept_packets는 성공한 제출 수, fallback_drop_packets는 그중 오류 정책 Drop 수다. logical_rule_drop_packets를 별도로 두고 simulated_drop_packets는inline에서0이다. PCAP/live는 기존 집계를 유지한다. run_complete는 생성 시점 정상 처리 중지이며 capture_complete는false, 최종 출력 성공은 logger_summary와 종료 코드가 확정한다. no fsync/동기 출력 지연/치명적 OOM 보장과 A6의 경미 보류는 유지한다.

## 격리 방화벽과 시험

별도 tests/check_inline_process.py 또는 scripts/run_inline_netns_test.sh가 namespace ID 차이와 Python 최적화 금지를 **if/raise로** 검사한 뒤에만 자체 table/chain/rule을 만든다. nft 실행 파일은 명시 경로로 전달하고 프로젝트 내부 추출본도 허용한다. 호스트 ruleset flush·호스트 인터페이스 변경·전역 서비스 시작은 없다. 익명 namespace 종료와 생성한 table 삭제로 정리한다.

테스트 규칙은 private namespace의 loopback IPv4 UDP 시험 포트만 queue로 보낸다. nft `bypass`를 사용하지 않으며 프로그램도 FAIL_OPEN을 켜지 않는다. listener가 없거나 종료한 상태에서는 해당 queued 트래픽이 DROP된다. 큐 포화/프로세스 crash의 범위는 커널 정책에 달려 있으며 일반망 fail-open 보장을 하지 않는다. 시험은 정상 종료 때 자체 규칙을 제거하고 namespace를 끝낸다.

실제 UDP 수신기에서 NORMAL/SAFE Pass/NOTICE Alert는 도착하고 BLOCKME Drop은 도착하지 않는지 확인한다. payload 원문은 로그에 저장하지 않는다. 그 상태에서 신호 종료, 빈 큐 종료, packet-count, 중복 바인딩/권한 거부, 로그 sink 실패/파일 크기 제한 후 실제 허용·차단 유지, listener 없음/종료 후 차단과 규칙 제거 후 통신 복구를 검사한다. TCP stream 판정과 L3 parser/error/guard 예외는 단위 테스트로 보강하고 실제 TCP 차단 일반화를 주장하지 않는다.

기본 CTest는 권한 없는 환경의 parser/controller/metadata/CLI/검증기 guard 회귀를 수행한다. 권한 있는 실제 NFQUEUE 시험은 각 Debug·Release/clang-tidy·ASan/UBSan에서 별도 실행한다. 미실행/권한·커널 실패는 skip 성공으로 숨기지 않는다. 기존238개, 포맷, JUnit·명령·소스/fixture/binary/도구 해시, 한 번의 독립 최종 리뷰와 중요 수정 근거를 보관한다. 동일 격리망의 수신 결과와 실제 verdict 카운터가 일치한 뒤에만 A7 완료다.
